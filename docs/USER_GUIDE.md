# Baraban / Project Alpha — инструкция пользователя

Актуально для версии **v0.3.13**.

## 1. Самый простой сценарий работы

Для обычной работы не нужно разбираться во всех технических полях.

1. Слева выберите нужный рабочий барабан. Поддерживаются разные механики, в том числе **«Alfa-Пятница — Tasty Coffee (30.09.2026)»** и **«Альфа-Онлайн — Суперкэшбэк (октябрь 2026)»**.
2. Получите рабочую сессию одним из двух способов:
   - предпочтительно: вкладка **«Сессия» → «Импорт capture ZIP»** и выбрать свежий ZIP из Network Recorder;
   - либо: вкладка **«Браузер / вход»**, открыть сайт и войти вручную.
3. На вкладке **«Браузер / вход»** убедитесь, что сайт открывается в авторизованном состоянии.
4. Вернитесь на **«Результат»** и нажмите расположенную там кнопку **«Запустить цепочку»**.
5. Смотрите результат в центральной таблице.

Автоматическая цепочка запускает только запросы, отмеченные в модуле как AutoRun, и **не запускает confirmation/mutating-запросы**.

---

## 2. Левая панель «Барабаны»

### Список барабанов

Выбирает активный модуль.

При выборе другого барабана приложение:
- загружает его исходные переменные;
- загружает HTTP-запросы и action-pipeline этого модуля;
- подставляет его адрес входа во вкладку браузера;
- очищает текущую таблицу результата.

Элемент с префиксом **[АРХИВ]** — исторический модуль. Для него автоматический запуск цепочки заблокирован.

### «Перезагрузить модули»

Повторно читает JSON-файлы модулей из:

`%LOCALAPPDATA%\Baraban\Drums`

Полезно после ручного изменения JSON-файла барабана.

Встроенные модули копируются туда только при отсутствии соответствующего файла. Эта кнопка **не сбрасывает пользовательские изменения к заводской версии**.

## 3. Вкладка «Результат»

На этой вкладке теперь находятся и запуск цепочки, и её итог.

Полосы прокрутки находятся внутри полей с данными и таблиц. Между полем переменных и таблицей результата есть разделитель, который можно перетаскивать мышкой для изменения высоты.

### «Переменные»

Это текущие runtime-переменные выбранного барабана в JSON-виде. JSON отображается форматированным с отступами.

Например:

```json
{
  "offerId": "21898",
  "advertCampaignId": "",
  "available": "[]"
}
```

Переменные используются в шаблонах запросов как:

`{{имяПеременной}}`

Они могут автоматически изменяться после ответов сервера.

Для обычной работы вручную редактировать их обычно не требуется.

### «Применить»

Разбирает JSON из поля «Переменные» и заменяет текущий набор runtime-переменных введёнными значениями.

Используйте только если осознанно хотите вручную изменить параметры выполнения.

JSON должен быть корректным.

### «Запустить цепочку»

Запускает автоматическую последовательность запросов выбранного барабана.

Перед запуском приложение:
- считывает текущие значения из поля «Переменные»;
- синхронизирует cookies из встроенного браузера;
- выполняет запросы с `AutoRun = true`;
- пропускает запросы с `IsConfirmation = true`;
- извлекает значения из JSON-ответов в переменные;
- строит итоговую таблицу.

Для архивного барабана автоматический запуск запрещён.

### Центральная таблица результата

Это основной вывод работы цепочки. До первого запуска отображается пояснение, что результат появится после запуска.

Колонки:
- `#` — порядковый номер;
- `offerDrumId` — идентификатор варианта/сектора;
- **Приз** — название;
- `offerId` — идентификатор предложения;
- **Результат** — для победившей строки отображается `★ WINNER`.

Победившая строка дополнительно выделяется. Если запросы выполнились, но строки не удалось спроецировать в результат, вместо пустого экрана показывается соответствующее сообщение.

## 4. Вкладка «HTTP»

Эта вкладка теперь объединяет работу с текущим барабаном в одном месте. Выпадающего списка запросов для обычной работы больше нет.

Верхние три кнопки задают нормальный рабочий сценарий:

### «Получить варианты призов»

Получает актуальный список вариантов и сохраняет его на экране в таблице **«Варианты призов»**.

Приложение выполняет описанный самим модулем pipeline. Например, старому Alfa-Friday могут потребоваться промежуточные `advertCampaignId`/`available`, а новый Alfa Online получает варианты непосредственно из `wheel-of-fortune`. Сам список после последующих действий не исчезает.

Таблица показывает:
- ID сектора;
- название приза;
- offerId, если он присутствует в ответе;
- состояние/текущий приз, когда состояние барабана уже было явно запрошено.

Парсер результата больше не требует обязательного `offerId`: он ищет массив призов в фактической структуре JSON и распознаёт вложенные поля.

### «Состояние барабана»

Получает текущее состояние.

После нажатия:
- ранее загруженный список вариантов остаётся на месте;
- приложение использует winner ID или `isWinner` из ответа — в зависимости от механики выбранного модуля;
- сверху блока состояния показывает **название текущего приза и его ID**, когда приз уже определён;
- полный ответ состояния остаётся доступен в таблице и в последнем HTTP response.

Если список вариантов ещё не был получен, приложение может получить его автоматически только для сопоставления названия.

### «Получить приз»

Это всегда явная mutating-операция, но конкретный API определяется выбранным модулем.

- Для Alfa-Friday это `confirmDrumOffer`: сервер уже сообщил winner ID, после чего пользователь отдельно подтверждает получение.
- Для нового Alfa Online с feature `NewClick_NewWheelOfFortune` это `PUT /api/v1/loyalty-view/accept` с `type: "DRUM"`: именно этот запрос выбирает выигрыш на сервере.

Перед отправкой приложение обязательно показывает подтверждение. Если победитель уже известен, показываются его название/ID; если новая механика выбирает победителя только при mutating-запросе, приложение прямо пишет, что приз будет выбран сервером после подтверждения.

Без ответа **Да** запрос не отправляется. Кнопка не входит в автоматическую цепочку и никогда не запускается сама.

### «Варианты призов»

Постоянная таблица вариантов. Она не очищается при запросе состояния.

### «Состояние барабана»

Отдельная область состояния. В ней крупно показывается текущий приз, а ниже — табличное представление ответа.

### «Последний HTTP response»

Снизу показан последний фактический HTTP-ответ:
- слева — небольшой raw JSON в pretty-формате;
- справа — более широкая структурированная таблица.

Между raw JSON и таблицей есть вертикальный разделитель: его можно перетаскивать мышкой.

Все корректные JSON-строки выводятся с отступами и нормальным Unicode. Последовательности вида `\u043E\u043A...` отображаются обычным русским текстом.

### Изменение размеров областей

Между **«Варианты призов»**, **«Состояние барабана»** и **«Последний HTTP response»** расположены горизонтальные разделители. Их можно подцепить мышкой и менять высоту областей.

Полосы прокрутки находятся внутри самих полей и таблиц. Главное окно приложения не должно прокручиваться на несколько экранов вправо.

### Расширенный режим

Внизу есть сворачиваемый блок **«Параметры последнего запроса (расширенный режим)»**.

Он сохраняет возможность просмотреть и изменить Method / URL / Headers / Body последнего рабочего запроса. JSON Body показывается в pretty-формате. Кнопка **«Сохранить параметры»** записывает изменения в пользовательский JSON модуля.

## 5. Вкладка «Сессия»

Здесь хранится HTTP/browser-сессия приложения.

Основной файл сессии:

`%LOCALAPPDATA%\Baraban\session.bin`

Он защищён Windows DPAPI для текущего пользователя Windows.

### Большое поле JSON

Редактируемое представление текущей сессии.

Основные разделы:
- `headers` — глобальные reusable headers;
- `requestHeaders` — headers, привязанные к конкретному Method + Host + Path;
- `cookies` — cookies;
- `browserStorage` — localStorage/sessionStorage импортированной страницы;
- `captureSource` — сведения об источнике capture;
- `updatedUtc` — время последнего сохранения.

Для обычной работы вручную это поле менять не нужно.

**В нём могут находиться действующие данные авторизации. Не публикуйте и не отправляйте содержимое этого JSON посторонним.**

### «Перечитать»

Отбрасывает несохранённые изменения в текстовом поле и заново загружает `session.bin`.

### «Сохранить JSON»

Название кнопки техническое: она **не создаёт обычный JSON-файл на диске**.

Она:
1. читает JSON из большого поля;
2. преобразует его в SessionProfile;
3. сохраняет защищённую сессию в `session.bin`;
4. применяет сохранённые cookies/storage ко встроенному браузеру.

### «Импорт Cookie header»

Ручной запасной способ импорта cookies.

В появившемся окне:

- **Domain** — домен cookies, по умолчанию `.alfabank.ru`;
- большое поле — значение HTTP-заголовка Cookie.

Вставлять нужно именно содержимое после `Cookie:`, например:

```
cookie1=value1; cookie2=value2; cookie3=value3
```

Сам текст `Cookie:` добавлять не нужно.

Этот способ беднее capture ZIP: обычный Cookie header не содержит полноценные expiry / HttpOnly / Secure / SameSite metadata.

### «Импорт capture ZIP»

Предпочтительный способ восстановления ранее записанной браузерной сессии.

Поддерживается формат Network Recorder:

`browser-session-capture`, `formatVersion = 2`.

Импорт:
- заменяет текущие session headers;
- заменяет request-specific profiles;
- заменяет cookies;
- импортирует localStorage;
- импортирует sessionStorage;
- сохраняет сведения о capture;
- сохраняет результат в `session.bin`;
- восстанавливает cookies/storage в WebView2;
- подставляет URL записи в поле браузера, если он известен.

После импорта сессия сразу отображается в форматированном JSON-представлении и применяется ко встроенному браузеру.

### «Очистить сессию»

Удаляет сохранённый `session.bin` и очищает HTTP-сессию в памяти.

**Профиль WebView2 при этом намеренно не удаляется.**

То есть сайт во встроенном браузере может по-прежнему оставаться авторизованным. При последующей синхронизации cookies браузер снова может наполнить HTTP-сессию.

## 6. Вкладка «Браузер / вход»

Это обычный встроенный браузер WebView2 с постоянным профилем.

Профиль хранится в:

`%LOCALAPPDATA%\Baraban\WebView2`

### Поле URL

Адрес, который будет открыт.

При выборе барабана сюда подставляется его `loginUrl`.

После импорта capture ZIP сюда может быть подставлен URL из записи.

### «Открыть»

Переходит на URL из поля.

Используется для обычной ручной авторизации или проверки восстановленной сессии.

### Область браузера

Полноценный WebView2.

Во время работы приложение автоматически наблюдает релевантные запросы браузера и сохраняет некоторые session/security headers, в том числе при необходимости request-specific профили.

После завершения навигации приложение также автоматически:
- применяет подходящий импортированный browser storage;
- считывает cookies обратно из WebView2;
- сохраняет обновлённую сессию.

### «Синхронизировать cookies»

Принудительно считывает текущие cookies из WebView2 и сохраняет их в сессию Project Alpha.

Обычно это нужно после ручного входа или если хотите явно зафиксировать актуальное состояние браузера.

## 7. Где находятся рабочие данные

Программа:

`%LOCALAPPDATA%\Programs\Project Alpha`

Рабочие данные:

`%LOCALAPPDATA%\Baraban`

Внутри:
- `Drums\` — редактируемые определения барабанов;

## 9. Новый барабан «Альфа-Онлайн — Суперкэшбэк»

Этот модуль относится к другому личному кабинету и использует другую серверную механику.

В capture от 02.10.2026 наблюдался:

`GET https://web.alfabank.ru/api/v1/loyalty-view/wheel-of-fortune?basketOfferId=21871`

Он сразу возвращает `offers[]` с ID сектора, категорией, размером кэшбэка, описанием и флагом `isWinner`.

Для активной в capture frontend-ветки `NewClick_NewWheelOfFortune` production-JS использует для прокрутки/получения приза:

`PUT /api/v1/loyalty-view/accept`

с `basketOfferId` и `type: "DRUM"`.

GET, две бесплатные/обычные прокрутки через PUT `/accept` и платная попытка через POST `/offer` теперь непосредственно подтверждены Network Recorder. Динамические security headers приложение не выдумывает и не делает глобальными.

Для этого кабинета сначала импортируйте именно свежий capture ZIP с `web.alfabank.ru`, затем выберите новый модуль и начните с **«Получить варианты призов»**.



### Повторная прокрутка

Для этого барабана кнопка mutating-действия меняется по фактическому состоянию сервера:

1. До первой прокрутки: **«Крутить скорее!»**.
2. После первого выигрыша сервер может вернуть **«Крутить ещё — 1 попытка»**. Это бесплатная повторная попытка.
3. Нажатие **«Крутить ещё»** не выбирает новый приз само по себе: приложение выполняет наблюдавшийся reset/refresh через `GET wheel-of-fortune`, очищает предыдущий winner в UI и возвращает кнопку **«Крутить скорее!»**.
4. Следующее **«Крутить скорее!»** снова вызывает `PUT /accept` и заменяет предыдущий выигрыш новым.
5. После второй прокрутки сервер может предложить **«Крутить ещё — за 49 ₽»**.
6. При нажатии Project Alpha показывает отдельное предупреждение о **реальном списании 49 ₽** и ничего не отправляет без ответа **Да**.
7. После подтверждения программа отправляет наблюдавшийся в capture `POST /api/v1/loyalty-view/offer`. Тело берётся из текущего `reconfirmButton.modalView.order` ответа сервера; account-specific данные в программу не зашиты.
8. Только если сервер вернул HTTP 2xx и `success=true`, попытка считается оплаченной. Кнопка становится **«Крутить скорее!»**.
9. Следующее нажатие выполняет безопасный GET-reset оплаченной попытки. Ещё одно **«Крутить скорее!»** выполняет обычный `PUT /accept` и получает новый `winnerOffer`.
10. В записанном платном цикле после оплаты выпало **«Аптеки — 7%»** (`winnerOffer.id=21931`).

Победитель всегда определяется из `winnerOffer.id` ответа mutating-запроса или dedicated winner GET. Поле `offers[].isWinner` в двух реальных прокрутках оставалось `false` для всех вариантов и не используется как источник победителя.
